# 独立审查与发现核对

用于 PR 前审查、PR 审查和复审。审查者检验实现是否满足意图，修复者负责获准修改；两者使用明确区分的上下文。

## 输入与产物

输入为意图、审查范围、基线与候选版本、项目规则和可用验证入口。输出为已核实发现、待验证疑点、已排除项，以及各自依据。

使用主流程已确定的范围和版本，不自行改为最后一次提交或扩大为全仓审计。项目规则和必需检查继续约束本方法。

## 组织审查

优先使用当前环境允许的独立审查会话或入口。向审查者提供原始目标、diff、规则和证据位置，不预先要求同意作者的结论。只有作者自检可用时明确报告，不能将其称为独立审查。

审查者保持产品代码只读。必要复现按项目约定与授权使用隔离位置，不影响其他运行中的任务。是否并行依据范围与权限，不要求每次启动固定数量的 Agent 或指定某个模型品牌。

## 审查重点

按正确性、安全、实际负载、有效测试、性能、必要复杂度的顺序检查相关改动。检查深度由具体行为与风险决定，不为凑齐条目制造问题。

| 重点 | 要核对的具体问题 |
|---|---|
| 正确性 | 输入、边界值、分支、状态和副作用是否符合意图；相关调用方能否继续使用 |
| 安全与数据 | 权限和不可信输入是否校验；错误传播、写入顺序和事务是否会泄漏或丢失数据 |
| 实际负载 | 按项目声明或运行证据检查竞态、进程间状态、无界增长和重复工作；负载未知时标明未知，不按假想规模要求重构 |
| 有效测试 | 风险逻辑是否有能发现行为错误的检查；看实际断言和替换的依赖，不用测试数量或覆盖率替代判断 |
| 性能 | 是否有与实际使用相关的明显退化；小幅优化通常作为建议，明确性能要求按项目规则处理 |
| 必要复杂度 | 是否存在确实未使用的代码、重复实现或无实际用途的抽象和选项；不按行数拆函数，不以个人风格要求改写 |

宣称代码未使用前，核查相关调用、配置、测试、字符串和动态入口。搜索无结果只是证据之一，不等于已经证明代码可删。

涉及 `shortcut:` 或旧 `ponytail:` 注释时，核对记录的局限和重新检查条件。条件仍成立时不重复提出已接受的局限；实际使用已超限时报告具体后果。缺少重新检查条件通常是改进建议。注释不能豁免安全、数据完整性或项目必需要求。

正例：配置通过字符串加载处理器，保留该实现；若某个有界队列的实际输入已超过注释中的上限，则核实并报告溢出后果。
反例：因直接调用搜索为空就建议删除处理器，或因有 `shortcut:` 注释而跳过权限缺陷。

## 核实发现

- 从真实输入和分支说明触发、后果及被破坏的契约。
- 核对文件、行号和版本；实际运行过的复现写清命令与结果。
- 静态依据与运行证据分开；缺少证明的疑点单列，不包装成确定缺陷。
- 合并同一根因的发现。区分新增问题、被激活旧问题和无关存量问题。
- 作者逐项核实后修复，或用依据说明误报、预期行为或范围外原因。

每项发现让读者知道这段代码做什么、何时出错、后果是什么、最小完整修复是什么。沿用主流程的严重性和证据格式。区分阻断项、非阻断改进与待验证疑点；精简建议没有实际缺陷或明确规则依据时，不自动作为阻断。

静态依据足以证实的问题可以报告，但不得标成运行复现。无法确认的疑点保留所缺证据和验证办法，不因环境不可达就自动判为无问题。没有发现仅表示本次范围内未发现问题，不代替必需检查、人工决定或平台审批。

复审核对新 diff、原发现是否解决及其关联影响。核心方案变化时补足影响分析。沿用主流程的轮次上限，不以另起会话或切换方法重置。

## 检查与边界

正例：审查者提出越权路径，独立核对其前提和实际结果后保留或撤回。
反例：因为多个 Agent 同意就视为已经证明，或审查者顺手改产品代码掩盖问题。

结果交回主流程的返修与人审步骤。没有核实发现是有效结果，不为填满报告制造问题。
