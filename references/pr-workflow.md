# PR 审查与复审

默认只读。先按 [审查对象与规则](review-target.md) 读取规则、锁定基线和受审版本，再查看差异。只加载实际使用的平台资料：[GitHub](platforms/github.md)、[Gitee](platforms/gitee.md) 或 [Git](platforms/git.md)。

## 首轮审查

使用 [独立审查方法](methods/adversarial-review.md) 检查正确性、安全、实际负载、有效测试、性能和必要复杂度，沿用已确定的规则、版本和范围。共享边界变化时结合 [变更影响核对](methods/blast-radius.md)。不要求固定数量或品牌的审查模型。

1. 读完整 diff、PR 意图、相关契约及正常和失败路径。跟随调用方与消费方核对影响。发现敏感边界时加深对应审查。
2. 按风险运行适用的已知检查，或读取已有结果。[验证方法](verification.md) 用于核对范围、状态与证据。
3. 核实每条发现。记录严重性、位置、触发条件、实际后果和验证依据。区分新增问题、受改动激活的存量问题、无关存量问题和待验证疑点。
4. 先报发现数量及关键影响。没有需修复项时直说。风格问题沿用既有自动检查。

## PR、CI 与线程

- 记录 PR、当前 head、目标基线及 CI 的实际验证提交。平台可以测试模拟合并结果，以它和本次 PR 的关联为准。旧版本的绿色结果不能证明新版本已验证。
- 读取必需检查、失败步骤、日志、行内意见和线程状态。线程标为已解决也要核对修复证据。
- 本地候选与远端 PR 不同时，分别列本地检查和远端 CI 的覆盖范围。缺失、跳过、超时或不满足规则的检查保留实际状态。
- 写评论、回记用户结论或推送返修提交只在对应操作已获授权时执行。标明技术意见与实际人工结论的来源。

## 返修后的复审

作者先核实发现，修复确认的问题，或附证据说明不适用。Agent 只在获授权时修改，并遵守下节的最小完整返修要求。查找本次影响范围内的同类问题，并复用原线程。

复审先比较上次受审提交和新提交，再核对原发现、相关调用链和复跑结果。基线或范围变化时回到完整 diff。没有新证据时不重复报告已处理事项。

每个 PR 默认最多完成三次 AI 审查。无阻断项时提前结束。网络重试、CI 重跑、同版本的重复事件和人工反馈不额外计轮。

第三轮仍有阻断项时暂停自动返修。核对已尝试的方法，说明为何未收敛，给出剩余阻断、可行替代方案、影响和验证办法。保留原计数。额外一轮需要明确的方案和授权。

## 人工审核

必需技术检查和阻断项处理完成后，为当前 PR 与 commit 准备 [人工审核材料](human-review.md)。通过、要求修改和暂缓均应明确记录。缺少必需检查、人工审批或关键证据时列出缺项。提交变化影响结论时，复核相关部分及平台规则。

## 最小完整返修

仅在已获修改授权时使用。先查共享根因及相关调用方，再选择能完整解决问题的最小修改。

- 优先复用仓库已有实现；其次考虑标准库或平台能力、已有依赖。遵守现有组件与接口约定，不为几行代码引入新依赖。
- 核对本次影响的调用方、测试、夹具、配置、导出及资源入口，一次补齐相关修改。无实际需要时不增加抽象、包装、选项或未来扩展。
- 移动、合并或删除代码时保留必要的校验、错误处理、安全和可访问性要求。差异更短不能成为漏修或降低验证的理由。
- 对新增或变更的风险逻辑，补能观察行为错误的针对性检查，并执行项目既定必需验证。一个小测试不是既有检查的上限；低影响文字不机械加单元测试。
- 如确需保留局限，记录具体限制及重新检查条件。注释不等于获得安全或数据约束的豁免。

正例：错误源于共享解析函数，修复该函数并核对调用方及相关检查。
反例：分别在多个调用方加补丁而遗漏共享根因，或为减小 diff 删除错误处理和失败断言。
