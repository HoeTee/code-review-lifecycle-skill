# PR 前、中、后的操作与 AI 往返

## 进入任务

先明确仓库、已有项目指令、任务目标、授权范围，以及当前是本地修改、未合并 PR 还是合并后故障。

- 平台从 remote、项目资料或用户说明识别，未知才问。
- 只读相应分支：[GitHub](platforms/github.md)、[Gitee](platforms/gitee.md)。其他平台请用户提供名称、操作文档或必要说明，按指定方式绑定，不强制装某个 CLI。
- 连接器/API/CLI 已满足任务时复用。需要安装才读取当前系统命令；只缺 Git 时读 [Git](platforms/git.md)。
- 分别验证工具、认证、仓库、PR 和 CI 所需能力，不用推送成功替代全部接入。
- 存在用户手册或明确指令时沿用；不兼容时指出具体差异，补必要步骤并保留依据。
- 记录所选平台、实例、仓库、分支、身份、手册、操作方式和已验证能力，凭据只存认证引用。

首次以用户启动的任务运行即可。需要事件自动执行时才配置实际工作流、Agent 调用和认证；Markdown 文件本身不会持续监听 PR。运行结束后仍无人值守需要真实服务与触发机制。

复用已确认接入方式与当前阶段。分批、结构迁移或重复检查时按 [执行效率](execution-efficiency.md)决定 PR 边界和需要重新验证的证据，不机械按目录层开 PR。

## PR 前

明确复现、已确认或待确认根因、预期、范围、影响和验收。执行 [验证方案](verification.md)，保持变更聚焦。使用环境允许的独立审查入口检查变更及相关调用链，处理有证据的问题。已有项目的修改前后提交约定继续遵守。

只读或仅提方案的任务不创建修改。新增业务方向或架构取舍先交用户判断，必要问题在此解决，不等最终人工关口。

## 五个交互点

| 时点 | 实际动作与证据 |
|---|---|
| 创建/复用 PR | 核对源与目标分支、当前提交；填写问题、行为变化、测试、风险和恢复说明；保存 PR 链接 |
| 读取 CI | 获取本次必需检查、状态、失败步骤和日志；分清代码、环境或工作流原因并验证修复 |
| 读取意见 | 获取技术 review、行内意见、讨论和处理状态；核对依据，不只读摘要 |
| 提交返修 | 在对应分支复现、修改、本地验证，推送新提交；更新变化的风险和证据 |
| 合并前复核 | 读最新 diff、检查、线程、冲突和人工记录；满足当前版本门槛后在既有授权内合并或交付合并 |

一个未合并 PR 可包含多个修复提交。无关需求另行记录，不在返修中扩大范围；合并后新故障需要新的修复 PR。

## CI 和合并规则

先复用已有执行器。根据验证矩阵创建或更新配置，实际运行成功后，再绑定准确检查名与账号兼容的合并规则。必需检查失败、超时、未完成或不符合既定跳过策略时不视为通过。

记录 PR 源 head、目标基础及 CI 实际验证提交，核对关联。平台可能测试模拟合并结果，不能要求 CI SHA 与源 head 永远相同。目标分支或提交更新后，按策略验证新的影响，不套用旧绿色结果。

线程“已解决”是处理状态，不能代替代码与测试证据。平台门槛来自实际配置，评论或聊天承诺不能自动阻止合并。

## AI 审查要求

首次读完整 diff，并核对 PR 意图、相关契约、调用关系、正常及失败路径。读取项目约定和 REVIEW.md，按变更风险选择深度；有实际敏感边界时补专项安全审查。

每项发现报告：严重性/是否阻断、文件与行号、触发条件、实际后果、依据与建议验证。区分新增问题、受改动激活的旧问题、无关存量问题、待验证疑点和误报。没有需修复项时直说，不为凑数量制造评论。

作者先核实意见，再修复或附依据处理误报。风格交给已有工具，避免无价值改写。同类缺陷检查本次影响范围内的其他实例，复用原线程；无新证据不重复报告已处理事项。

复审围绕新增 diff、原发现是否解决和关联影响，保留必要上下文。范围或核心方案变化时重新评估完整影响，不因“只看 diff”漏掉调用方。

## 自动往返上限

默认每个 PR 的 AI 往返最多完成三次审查，计数保存于任务/PR 记录并绑定版本，恢复任务时继续已有计数。

| 完成的审查 | 后续 |
|---|---|
| 第 1 次审 A | 无阻断项就结束循环；否则在授权内修成 B |
| 第 2 次审 B | 无阻断项就结束循环；否则修成 C |
| 第 3 次审 C | 无阻断项进入人工关口；仍有阻断项就暂停自动返修 |

用户启动后无需每轮批准。CI 重跑、网络重试、同一版本的重复事件与人工反馈不额外计轮。三轮不是同一份代码反复查三遍，也不要求凑满。

第三轮未通过，先停止原补丁循环，Agent 自行完成一次有界的方案复盘：判断为何未收敛，是方案缺陷、同类漏检、检查不足、环境问题还是契约冲突；核对已有发现与已尝试办法，给出具体替代做法、影响和验证计划。必要时建议收缩或重做，不默认推翻整个项目。

然后交付未解决项、证据、复盘结论和明确推荐，列出真正需要人的需求、范围、重大风险或新增执行预算决定。普通技术分析由 Agent 完成，不能只问“要不要再审一轮”。复盘本身不计新的代码审查，也不授权继续修补或第四次审查；额外执行需有具体新计划和明确授权，保留原计数。

这是失败后的方案决策，和技术通过后的最终人工审核分开标识。正例：发现多次遗漏迁移入口，Agent 先核对全部消费方并给出执行入口验证方案，再就超出原上限的尝试请求决定。反例：同一做法再补一行就称为“换方向”，或把同意继续修复当作批准最终合并。

不能自动关闭 PR、放行、拆出相同任务重置计数或无限加补丁。需求冲突、重大取舍或超出授权立即交给用户，不等第三轮。改变默认上限需明确更新约定。

## 人工与后续

CI 与 AI 审查可并行。默认人工最终审核看处理完成后的版本，按 [人工审核](human-review.md)交付材料，并等待用户明确结论。平台要求人类审批时由实际有资格的人完成，AI 不代替；调查单人账号的自审限制，避免配置不可满足的规则。

合并前再次读取当前 head、对应检查与人审范围。新提交影响结论时补验证并再次确认受影响部分；遵守平台对旧审批失效的实际规则。不要因一次历史“同意”批准以后所有提交。

合并后按 [交付与故障分流](delivery-recovery.md)记录实际合并 commit 与后续状态。
