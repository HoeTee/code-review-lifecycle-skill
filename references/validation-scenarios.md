# 审查场景验证

| 场景 | 应看到的行为 |
| --- | --- |
| 用户只说「做下 code review」 | 自动定位仓库，先读适用规则，确定版本与基线；AI 在本次范围内修复已确认缺陷、验证和复审，不逐项等待许可。 |
| 用户明确「只读审查，只给报告」 | 读取和验证可确认范围，不修改产品、验证工具或规则文件。 |
| AI 首轮发现可确认的解析错误 | 主 Agent 修复、验证，再由只读独立审查角色检查新版本；通过后准备最终人审材料。 |
| 本地修复已完成，但没有远端写入授权 | 交付本地修复与证据，标明远端 PR 尚未更新；不推送或把旧 CI 记到新版本。 |
| 在有额外改动的分支 B 审 PR A 并发现缺陷 | 从 A 的固定 head 准备隔离工作树返修，保留 B 的原内容；验证与复审对应新候选，不能在 B 直接修改同名文件。 |
| 人工最终检查要求修改 | 回到 AI 阶段，继承已有轮次；修复和相关验证完成后再次检查受影响部分，上限用尽则交复盘。 |
| 根 CLAUDE.md 和 REVIEW.md 都缺失 | 调查现有资料，调用内置方法给完整草案并请用户确认；确认前不写入，独立审查继续。 |
| 只缺 REVIEW.md，已有等价 AGENTS.md | 保留已有规则，只为缺失文件起草，引用已有事实而不重复另一套要求。 |
| 起草规则时缺少架构或业务依据 | 从真实入口整理模块、接口与状态归属；未知项标待确认并问必要问题，不编造实现或命令。 |
| 用户认可规则草案，但尚未审核产品变更 | 仅按确认内容与授权补齐规则，不能记录为当前 PR 已获人工批准。 |
| 项目要求同步落盘，架构方法偏向异步 | 方法继续按现有契约调查，异步方案另列建议；不能改写契约或启动设计流程。 |
| 只需核对调用链，存在六个内置方法 | 由入口选 how 并读取全文，设计依据不足时再读 why；不加载所有方法或依赖它们自动触发。 |
| 适用规则在同一条件下要求不同结果 | 列出具体来源、原文及影响；按宿主规则和明确要求核对，无法消解的业务取舍请用户决定，独立部分继续。 |
| 可信规则引用缺文件，或必需命令入口缺失 | 报告具体路径、影响及下一步，不能标已读或通过；只读审查不自动补建。 |
| 当前分支有提交，工作区干净 | 取得分支差异，记录确认的基线和 head。 |
| 已绑定 PR，同时本地另有改动 | 审远端 PR head，另列本地额外改动。 |
| 未绑定 PR，本地候选比远端新 | 审本地候选，远端 CI 标明它实际覆盖的版本。 |
| 本地既有暂存也有未暂存内容 | 区分工作区快照与下一次提交的内容，记录审查范围。 |
| 已提交代码导入尚未跟踪的新文件 | 从状态中的 `??` 识别该文件，读取并纳入混合候选审查。 |
| PR 修改 REVIEW.md 或适用的目录规则 | 先加载可信基线规则，把规则修改作为差异审核。 |
| 根 REVIEW.md 未变，候选修改它引用的规则 | 从同一可信提交读取根文件和引用文件，把修改作为差异审核。 |
| 两次查询之间 PR 的 base 或 head 变化 | 用固定 SHA 生成差异，或丢弃按编号取得的差异并重新取证。 |
| GitHub 或 Gitee 只读权限 | 取得可用 PR、检查和讨论证据，缺项明确报告。 |
| 第三轮仍有阻断 | 保留计数，停止自动返修，给有依据的下一步。 |
| 本地完成两轮审查后创建同一任务的 PR | 继承计数，默认最多再完成一轮，不新增三轮。 |
| 两次修复共享同一前提但同一检查仍失败 | 下一次修改前直接验证前提并记录观测；已到轮次上限则只复盘，不借调查继续返修。 |
| 同类缺陷在不同入口至少出现两次 | 只读时建议，获准返修时修共享根因或补有效检查；证明坏行为失败、修复后通过并复用既有验证入口。 |
| 更换审查方法或上下文后继续同一 PR | 沿用已确定的范围、版本与轮次，不能缩成最后一次提交或重置三轮上限。 |
| 配置通过字符串动态加载处理器 | 核对配置、字符串、动态入口与相关调用，不能因直接调用搜索为空就建议删除。 |
| shortcut 局限仍适用，另有被注释掩盖的权限缺陷 | 不重复已接受局限，仍报告有依据的安全问题；注释不能豁免必需要求。 |
| 实际负载已超过 shortcut 中的局限 | 核实具体后果并按项目标准分级；没有重新检查条件通常列为改进建议。 |
| 没有实际负载证据，代码可以更抽象或更短 | 标明未知，不按假想规模要求重构；无实际缺陷或规则依据的精简建议不自动阻断。 |
| 当前环境无法运行，但源码显示可达的缺陷 | 分开报告静态依据、运行状态与待验证疑点，不声称已复现或自动判无问题。 |
| 项目有多项必需检查，返修只新增一个小测试 | 仍满足既有必需检查；测试数量不能作为缩减验证的理由。 |
| 多个调用方因共享解析函数而失败 | 获准后优先修共享根因，核对调用方、测试及配置，保留错误处理和失败断言。 |
| 新提交影响已审核结论 | 重新检查受影响的发现和验证结果，结论绑定新版本。 |
| 需要人工决定 | 显示关键代码、证据、待决定项、对应 PR 和 commit。 |
| 报告含未解决 P1/P2、已修复 P1 和风格建议 | 仅汇总未解决 P0/P1/P2，按级别排序；已修复、疑点、建议另列，每项标证据、状态及是否阻断。 |
| 无已确认发现，项目使用自有严重性级别 | 报 P0/P1/P2 均为零，保留项目标准及必要映射；不能制造 P2 或降低门槛。 |
| 准备简单改动的人审报告 | 仍按主入口给聊天与 HTML，图可省略；用户另有要求或渲染失败按实际情况处理。 |
| 项目事先规定一项发布后目标检查 | 合并前必需检查照常满足，单列发布后待验收、依据和责任，不标通过；不可达不自动形成例外。 |
| 三个 Agent 安装 | 共用一个入口，能调用随包渲染器。 |
| 通过 CLI 准备混合候选 | 完整 tracked diff、暂存信息与未跟踪文件被记录，规则及引用从同一可信来源读取。 |
| 正常一轮提交审查 | prepare 返回 next 与模板；verify 直接执行指定命令和标准 JSON；record、render、validate 分别保存、生成、校验，在一次宿主调用中依次执行，不另写整理脚本。 |
| 独立动作不重复执行 | render 不重记审查或运行测试；validate 不重渲染；篡改页面或更新记录后旧校验失败；缺陷 ID、open 状态和 P0/P1 阻断由工具补入，明确阻断不能被覆盖。 |
| 报告失败后重试 finish | 保留完成轮次，复用原输入重试不重复计轮；版本变化不能沿用旧结论。 |
| 结果文件未更新、缺失或计数错误 | 必需检查失败，不使用旧文件伪装本轮结果；原始退出码、快照与跳过依据继续保留。 |
| 同一审查结果重试记录 | 相同 ID 和内容不重复计轮；异内容拒绝，换 PR 或会话不重置已有轮次。 |
| 新 CI 失败后旧成功迟到 | 按观察时间保留新失败，不能进入最终批准。 |
| 更换计划只保留一个快速检查 | 历史必需检查不消失，未满足时不请求最终检查。 |
| 本地任务关联新 PR，或确认根规则后继续 | 同一状态更新关联及可信规则来源，保留轮次；未提交规则可冻结确认内容，候选后续修改不能替换它。 |
| 宿主未提供 token 用量 | 实际用量显示未知，CLI stdout 粗略估算单列，不称为真实计费或节省率。 |
| 重复导入同一请求用量 | 请求 ID 去重，输入和输出不重复累计缓存与推理子项。 |
| 新旧进度快照 | 都能渲染，报告显示审查目标的证据与链接，并保留检查原记录时间。 |
| 生成或局部更新 HTML | 页首项目名和 Star on GitHub 指向本项目。 |
| 生成 answer-me-with-html 说明页或审查报告 | 检查生成命令、HTML 文件、关键正文、证据和链接，不截图或启动视觉验收。 |
| 被审查产品使用 HTML，验证要求截图 | 驱动实际产品并保留所需截图，可将截图作为证据放入审查报告。 |

验证记录应包括输入、实际执行和覆盖范围。结构与链接检查、场景走查和真实 Agent 执行分别报告。
