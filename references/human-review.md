# Agent 怎样帮助人工审核

人工审核是 PR 创建后、合并前的明确关口。展示位置可以是当前对话、网页或 Git 平台，结论始终绑定同一 PR 和确切版本。

## 原则

先给人一页能判断的材料，再按其需要展开。审核对象是行为变化、关键逻辑及风险；不要把完整脚本或一串绿色检查作为唯一材料。始终保留完整 diff 与源码入口，片段不能隐藏重要条件或调用影响。

按 [进度与交互](progress-interaction.md)更新同一任务入口。进入人审时首屏突出具体待决定项、推荐、影响和关键片段；聊天同步该问题，证据供展开查看。没有正式待决定项时不把普通交付标成“等待批准”。

这是把原文“为需要理解的代码局部生成 explainer”落实为审核材料的做法，不是声称原文规定了固定模板。
来源：[Sharing context across the team](https://claude.dev/blog/solving-code-review-at-anthropic/)。

## 选择片段

1. 从 PR 目标和实际 diff 识别行为变化点，优先副作用、权限、状态、数据、边界、错误处理及配置消费。
2. 片段给出文件、已核实的行号及对应 commit。需要时显示前后版本。
3. 为理解保留入口、调用方、被调逻辑、前置条件与输出消费方，片段长度按因果链决定，不机械限行数。
4. 纯重排不与关键业务修改争夺注意力；提供可查入口即可。高影响修改展开更充分证据。
5. 人看不懂时换用该仓库真实代码继续解释，不让其自己复制文件，也不改用无关发明例子。

## Explainer 至少回答

- 这段原来做什么，现在改变什么，为什么需要改。
- 谁调用它，哪些输入来自用户、配置、状态或上游字段。
- 内部关键条件如何选择分支，哪些函数真实执行。
- 输出、状态与副作用传给谁；跨脚本、进程或 API 的交接是什么。
- 失败、取消、超时或异常如何传播；该变更怎样影响调用方和最终产物。
- 哪些结论有执行证据，哪些仅静态推断，尚缺什么验证。
- 现有检查能拦住什么、会漏什么，需要人判断什么。

按用户理解程度解释必要术语。简单改动用短文与片段；复杂关系按需生成一页 HTML、调用图或数据流图。解释必须来自当前代码和配置，并附源码入口。没有图形工具时普通 Markdown 也能完成，不把网页生成器设为必装依赖。

## 默认审核包

| 内容 | 要求 |
|---|---|
| 对象 | PR 链接、源 commit、目标分支及 CI 对应版本 |
| 目标与范围 | 原问题、预期、修改前后行为、相关路径和不确定项 |
| 关键片段与 explainer | 按上述规则解释实际因果链；附完整 diff |
| 技术证据 | 本地和 CI 的实际命令/结果，AI 发现与处理，已验证/未验证范围 |
| 业务结果 | 可打开或查看的实际产物、关键场景结果及剩余风险 |
| 用户决定 | 列出需要业务或架构取舍的具体问题，给建议及理由；请求通过、修改或暂缓 |

资料不足先补证据，不能把未知正确性交给非技术用户盲目签字。Explainer 不是测试或独立审查的替代品。不要用只挑成功路径、遗漏关键信息的说明包装改动。

## 记录与后续

默认在当前对话展示材料，用户也可直接在平台审核。记录 PR、commit、用户原话结论、证据及未解决项，不把沉默或“看到了”当作通过。用户只同意方案，不等于已验收实现。

有授权时把结论与来源记录到 PR；由 Agent 代记时标明“用户结论代记”，不能伪装用户账户的 review。不能写平台时保留绑定版本的本地记录，明确远端尚未记录。

聊天验收首先约束 Agent 流程，不自动等于平台原生 Approve。按平台实际权限和既有规则满足合并门槛；例如 GitHub PR 作者不能批准自己的 PR。不得用机器人审批冒充第二个人，或为了通过而绕过已有保护。
[GitHub 审批说明](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews)。

新提交、基线或配置变化影响已审核结论时，重新验证并请人核对受影响部分；保留仍成立的证据，按平台规则处理旧审批。通过后在已有授权内进入合并或交付合并，不擅自扩大为发布、部署或恢复授权。
